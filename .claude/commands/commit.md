현재 작업 트리의 변경 내용을 정리해서 커밋한다. 사용자 인자: $ARGUMENTS (있으면 커밋 범위·메시지 힌트로 활용)

## 절차
1. `git status`와 `git diff`(staged/unstaged 모두)로 전체 변경을 파악한다.
2. **논리적 단위로 그룹핑**한다. 서로 다른 관심사(기능 구현 vs 문서/도구 설정 등)는 별도 커밋으로 나눈다.
   - 이미 staged/unstaged가 관심사별로 나뉘어 있으면 그 경계를 존중한다.
3. 각 그룹을 `git add <경로>`로 스테이징하고 커밋한다. 여러 커밋이면 순서대로 반복한다.

## 커밋 메시지 규칙 (이 프로젝트)
- **한국어**로 작성한다.
- 형식: `<type>: <요약>` — type은 feat / fix / docs / chore / refactor 중 선택.
- 기능 커밋이면 관련 유저스토리 ID(US-0XX)와 버전을 요약에 포함한다.
- 본문은 `-` 불릿으로 변경의 "무엇을·왜"를 적는다.
- 메시지 끝에 반드시 다음 푸터를 붙인다:

  ```
  Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
  ```

## 규칙
- 커밋만 한다. **push는 사용자가 명시적으로 요청할 때만** 한다.
- 이 저장소는 `main`에서 직접 커밋하는 단일 개발자 워크플로우다(기존 히스토리 관례). 별도 브랜치를 만들지 않는다.
- 커밋 전 `harness/`·상태 문서 등 무관한 파일이 섞였는지 확인하고, 관심사에 맞게 분리한다.
- 삭제·덮어쓰기 대상이 있으면 먼저 내용을 확인한다.
- 완료 후 `git log --oneline -N`으로 결과를 요약해 보고한다.
