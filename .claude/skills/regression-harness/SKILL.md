# 회귀 방지 하네스 스킬

기존에 배포/승인된 화면과 기능은 **불변(frozen)** 자산이다.
새 기능은 기존을 변경하지 않고 **추가(additive)**로만 구현한다.

## 구성
```
harness/
├── manifest.json          # 보호 대상 경로, 테스트 명령 설정
├── baseline.sh            # 기준선 캡처 (갱신은 사용자 승인 전용)
├── check.sh               # 통합 검사 (파일 무결성 + API 호환 + 테스트)
├── openapi_diff.py        # API breaking change 탐지
├── baselines/             # 캡처된 기준선 (git 커밋 대상)
└── last-report.md         # 마지막 검사 상세 리포트
```

## 에이전트 필수 절차

### 구현 시작 전
1. `./harness/check.sh --fast` 실행 → 시작 시점이 깨끗한지 확인
2. 깨져 있으면 새 작업을 시작하지 말고 오케스트레이터에 보고

### 구현 중 (Additive-Only 원칙)
- 기존 화면 수정 대신 **새 화면/컴포넌트/모듈 추가**
- 기존 API 수정 대신 **새 엔드포인트 추가** 또는 **optional 필드 추가**
- 기존 컴포넌트에 기능이 필요하면: 수정하지 말고 확장(컴포지션/새 variant) 우선
- 공용 파일(tokens.json, 라우터, DI 설정 등)에 추가는 허용하되
  **기존 항목의 값 변경·삭제는 금지**
- 기존 테스트 파일을 수정해 통과시키는 것 금지 (테스트가 곧 기존 동작의 명세)

### 완료 보고 전
1. `./harness/check.sh` 전체 실행
2. **통과한 경우에만** 오케스트레이터에 완료 보고 (리포트 경로 첨부)
3. 실패 시: 침범한 파일을 원복하고 additive 방식으로 재구현

## 기존 변경이 불가피할 때 (승인 절차)
기존 화면/API 변경이 정말 필요하면:
1. 에이전트는 변경하지 말고 **변경 제안서**를 오케스트레이터에 제출
   (무엇을, 왜, 영향 범위, 하위 호환 대안 검토 결과)
2. 오케스트레이터는 사용자에게 승인 요청
3. 사용자 승인 후에만: 변경 → 사용자가 `./harness/baseline.sh --approve <스토리ID>` 실행
4. baseline-history.log에 승인 이력이 자동 기록됨

**에이전트는 어떤 경우에도 baseline.sh --approve를 스스로 실행하지 않는다.**

## 새 기능 배포 후
기능이 게이트를 통과해 "기존"이 되면, 사용자 승인 하에 베이스라인을 갱신해
방금 추가한 것들도 보호 대상에 편입한다.

## API 호환성 기준 (openapi_diff.py가 검사)
| 허용 (additive) | 금지 (breaking) |
|---|---|
| 새 엔드포인트 추가 | 엔드포인트/메서드 삭제 |
| optional 필드 추가 | 응답 필드 삭제 |
| 새 enum 값 추가 | 필드 타입 변경 |
| 새 optional 파라미터 | 필수 파라미터/필드 추가 |
| | enum 값 삭제 |
