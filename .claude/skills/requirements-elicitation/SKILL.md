# 요구사항 인터뷰 스킬

PRD를 추측으로 쓰지 않는다. 요청이 들어오면 먼저 **인터뷰 파일**을 만들어
사용자에게 질문하고, 답변을 반영한 뒤에만 PRD를 작성한다.

## 인터뷰 파일: docs/requirements-interview.md

```markdown
# 요구사항 인터뷰: <기능명>
상태: WAITING_FOR_USER | ANSWERED | CLOSED
라운드: 1/2

## 요청 원문
(사용자가 처음 말한 내용 그대로)

## 내가 이해한 것 (확인용 요약)
- ...  ← 사용자가 틀린 부분을 바로잡을 수 있게

## 질문
### Q1. [사용자] 이 기능의 주 사용자는 누구인가요?
- (a) 일반 방문자  (b) 가입 회원  (c) 관리자  (d) 기타: ___
- 기본 가정: (b) — 답이 없으면 이 가정으로 진행합니다

### Q2. [범위] ...

## 답변 (사용자/오케스트레이터가 채움)
- Q1:
- Q2:
```

## 질문 설계 규칙
1. **6개 카테고리에서 골라 5~8개만** (전부 묻지 않기 — 요청에서 이미 파악된 건 질문 금지):
   - [사용자] 누가 쓰나, 어떤 상황에서
   - [문제] 지금 뭐가 불편한가, 왜 지금 필요한가
   - [범위] 반드시 포함 / 이번엔 제외 (Non-goals 후보)
   - [데이터] 어떤 정보를 다루나, 민감정보 여부
   - [제약] 일정, 기존 시스템 연동, 정책/법적 제약
   - [성공] 무엇이 되면 성공인가 (측정 방법)
2. **모든 질문에 선택지 또는 예시**를 붙인다 — 열린 질문만 나열하면 사용자가 답하기 어렵다
3. **모든 질문에 기본 가정을 명시** — 무응답 시 그 가정으로 진행 (인터뷰가 블로커가 되지 않게)
4. 한 질문에 하나만 묻는다 (복합 질문 금지)
5. 기술 구현 질문 금지 (스택·아키텍처는 개발자 몫)

## 라운드 규칙
- **최대 2라운드.** 1라운드 답변에서 새로운 핵심 불확실성이 드러난 경우에만 2라운드
- 2라운드 후에도 불명확한 항목은 PRD의 "확인 필요(Open Questions)" 섹션으로 이관하고
  기본 가정으로 진행 — 인터뷰를 무한 반복하지 않는다
- 답변받은 내용은 PRD에 반영하고, 인터뷰 파일 상태를 CLOSED로 변경

## 오케스트레이터 연계 (중요)
- planner는 사용자와 직접 대화할 수 없다. 질문은 반드시 인터뷰 파일로 작성하고
  "WAITING_FOR_USER 상태입니다. 사용자에게 질문을 전달해주세요"라고 보고하며 종료
- 오케스트레이터는 파일의 질문을 사용자에게 그대로 전달하고
  (Claude Code의 질문 UI가 있으면 활용), 답변을 파일의 답변 섹션에 기록한 뒤
  planner를 재호출한다
