## 개요

`design/v2.0.0/레시피 상자.html` 목업 중 기존 7개 화면에 없던 기능을 확장했다. 신규 도메인 필드(조리시간·회원 평점 집계·식재료 마스터 확장·재고 보관위치)와 홈 대시보드, 그리고 화면 간 UX 연결(요리시작·부족재료 연결·매칭바·재고 역탐색·재고 위저드)을 추가한다. 기존 7개 화면의 구성·라우팅·동작은 보존한다(additive).

## 포함 기능 (US-014~022)

| ID | 기능 | 계층 | 설명 |
|---|---|---|---|
| US-014 | 조리시간 | Must | 레시피에 `cook_time_minutes`(분) 추가. 목록/상세 표시, `sort=cook_time_asc` 정렬(미입력은 뒤로). |
| US-015 | 별점(회원 평점 집계) | Must | 여러 회원의 1~5 평점을 모아 평균·평가 수 집계. 1인 1평점 upsert. `sort=rating_desc`. |
| US-016 | 식재료 마스터 확장 | Must | 별칭(aliases)·kcal_per_100g·보관방법(default_storage)·메모 추가. 별칭 검색(`q`) 매칭. |
| US-017 | 재고 보관위치 | Must | 재고 항목에 `storage_location`(냉장실/냉동실/실온). 매칭 판정 미반영. |
| US-018 | 홈 대시보드 | Must | 신규 `/home` 라우트 + `GET /dashboard`. KPI 4종 + 패널 3종 집계. |
| US-019 | 요리시작·부족재료 연결 | Should | 레시피 상세→부족 재료를 재고/추천 흐름으로 연결. |
| US-020 | 매칭률 진행바 | Should | 보유/필요 재료 매칭률을 진행바로 시각화. |

| US-022 | 재고 위저드 | Could | `/inventory?wizard=1`로 다단계 재고 입력. 기존 단일 `InventoryAddForm` 보존. |

## 계약 변경 (openapi v2.3.0, additive · 하위호환)

`openapi.yaml` `info.version` → **2.3.0**. 모든 변경은 **additive-only**이며 기존 소비자는 신규 필드를 무시하면 된다(필드 삭제·타입 변경·필수화 없음). 회귀 하네스 계약 하위호환 검사 통과.

### 신규 엔드포인트

- `PUT /recipes/{recipeId}/rating` — 내 별점 등록/수정(US-015, 1인 1평점 upsert). 로그인 필요. 갱신된 평균·평가 수·내 평점 반환.
- `DELETE /recipes/{recipeId}/rating` — 내 별점 취소(soft delete). 로그인 필요. 재계산된 집계 반환(`my_score`=null). 취소할 평점 없으면 404.
- `GET /dashboard` — 홈 대시보드 요약(US-018). **로그인 필요**(개인 재고 기반). KPI 4종(등록 레시피 수 / 지금 만들 수 있는 레시피 수 / 내 재고 종수 / 임박 재료 D-3 수) + 패널 3종(만들 수 있는 레시피 / 유통기한 임박 / 최근 추가 레시피).

### 신규 정렬 옵션 (`GET /recipes` `sort`)

- `rating_desc` — 평균 평점 높은 순(평가 없는 항목은 뒤로, US-015).
- `cook_time_asc` — 조리시간 짧은 순(조리시간 없는 항목은 뒤로, US-014).
- 기존 `recent`(기본)·`missing_asc`는 불변.

### 신규 필드 (모두 optional/nullable, 읽기 기본)

- `RecipeDetail` · `RecipeListItem`(읽기): `cook_time_minutes`(nullable int), `rating`{`average`(nullable), `count`}.
- `RecipeWriteRequest`(쓰기): `cook_time_minutes`.
- `Ingredient`: `aliases`(기본 []), `kcal_per_100g`, `default_storage`(냉장/냉동/실온), `memo`.
- `InventoryItem` · `InventoryWriteRequest`: `storage_location`(냉장실/냉동실/실온).

## DB 마이그레이션 — `server/app/migrations/002_v230.sql`

**Additive-only**: 모든 신규 컬럼은 `ADD COLUMN`(nullable), **백필 없음**(기존 행 NULL). 기존 컬럼/테이블/인덱스 변경·삭제 없음. enum 값은 앱 계층(Pydantic Literal)에서 검증하며 CHECK 제약은 신규 테이블에만 둔다.

### 변경 내역

- `recipes.cook_time_minutes INTEGER` (US-014)
- `ingredients.aliases_json TEXT` / `kcal_per_100g REAL` / `default_storage TEXT` / `memo TEXT` (US-016)
- `inventory_items.storage_location TEXT` (US-017)
- 신규 테이블 `recipe_ratings`(id, recipe_id, user_id, score CHECK 1~5, created_at, updated_at, deleted_at) + 인덱스 (US-015)
  - 활성 행 기준 1인 1평점: `UNIQUE INDEX ux_recipe_ratings_recipe_user_active (recipe_id, user_id) WHERE deleted_at IS NULL`
  - 조회 인덱스: `ix_recipe_ratings_recipe (recipe_id)`

### 적용 절차

- 마이그레이션은 앱 **기동 시 FastAPI lifespan의 `run_migrations()`가 자동 적용**한다(파일명 사전순, `schema_migrations`로 idempotent 중복 방지). 별도 수동 명령 없음 — 새 버전 배포 → 앱 기동 → 자동 적용.
- 배포 **직전** `DB_PATH` 파일을 스냅샷(복사)해 둔다(롤백 대비).

### 되돌리기(롤백)

- 마이그레이션은 **전진 전용(forward-only)** — 코드를 v2.0.0으로 되돌려도 스키마는 자동으로 내려가지 않는다.
- `002_v230.sql`은 **additive(nullable ADD COLUMN + 신규 테이블)** 이므로 구버전 코드가 남은 컬럼/테이블을 무시하고 정상 동작한다 → **애플리케이션만 롤백하면 안전**(스키마 되돌림 불필요).
- 데이터 레벨 복구가 필요한 심각한 손상 시에만 배포 직전 스냅샷으로 `DB_PATH`를 복원한다. 절차는 `deploy/README.md` 7절 참조.

## 결정 사항

- **비로그인 공개 표시**: 조리시간·평균평점은 비로그인 사용자에게도 **공개 표시**한다.
