# 레시피 & 식재료 관리 웹서비스 PRD
버전: 0.2 | 작성일: 2026-07-24 | 상태: Approved (G1 통과, 사용자 승인 2026-07-24)

> 근거: 모든 주요 결정은 `docs/requirements-interview.md`의 답변(Q1~Q7)과 연결된다.

## 1. 문제 정의
- **누가**: 요리를 하는 여러 일반 회원 (각자 자기 레시피/식재료를 관리) *(Q1-b)*
- **상황**: 자신의 레시피를 흩어진 메모·캡처로 관리해 다시 찾기 어렵고, 집에 어떤 재료가 있는지 파악이 안 돼 중복 구매·재료 낭비가 생긴다.
- **불편**: (1) 내 레시피를 구조화해 저장·검색할 곳이 없다. (2) 보유 재료와 레시피가 연결되어 있지 않아 "지금 있는 재료로 뭘 만들 수 있는지" 알기 어렵다.

## 2. 목표 & 성공 지표
- **목표(정성)**: 개인이 자신의 레시피와 보유 식재료를 한 곳에서 등록·검색·관리하고, 보유 재료 기준으로 레시피를 활용할 수 있게 한다.
- **지표(정량, 소규모 기준 — Q6-a)**:
  - 회원이 레시피를 등록하고 다시 검색해 찾는 핵심 플로우 성공률 ≥ 95%
  - 레시피 상세에서 "내 재고 대비 부족한 재료" 표시가 재고 데이터와 100% 일치
  - 레시피 목록/검색 응답 체감 지연 1초 이내 (레시피 수백 개 규모 기준)
  - 등록/수정 시 비로그인 사용자가 로그인 유도 화면으로 100% 안내됨

## 3. Non-goals (이번에 하지 않는 것)
- 장보기 목록 / 자동 쇼핑리스트 생성 — **명시적 제외** *(Q3-a → MoSCoW Won't)*
- 영양성분·칼로리 계산 *(Q3, 미선택 → 이번 범위 밖)*
- 레시피 공개 공유·댓글·좋아요 등 소셜 기능 *(Q3, 미선택 → 이번 범위 밖; 열람 자유이나 "공유 발행"은 아님)*
- 식단 캘린더 / 주간 식단 플래너 *(Q3, 미선택)*
- 외부 쇼핑몰·배달 연동 *(Q3, 미선택; Q7 외부 연동 제약 없음)*
- 팀/가족 공동 편집, 관리자 콘텐츠 운영 *(Q1에서 다수 개인 회원 선택 → 공유 그룹·관리자 모델 제외)*

## 4. 유저스토리

> **범위 배분 주의(중요):** 사용자는 Q2에서 5개 기능(레시피 CRUD·식재료 CRUD·검색/필터·재고관리·보유재료 추천)을 모두 MVP로 선택했다. 그러나 규모는 소규모(Q6-a)이고 현실적 MVP(약 2~4주)를 목표로 하므로, 서로 의존관계가 있는 기능을 계층화했다. 기반이 되는 CRUD·검색·연동은 **Must**, 재고 관리와 부족 재료 대조는 **Should**, 계산 복잡도가 높은 "보유 재료 기반 추천"은 **Could**로 배분한다. 이 배분은 planner의 권고이며, 사용자가 5개 전부를 1차 출시 필수로 고정하려면 일정이 늘어남 → 5절 Open Questions 참조.

### 인증 (Q4-c: 열람 자유, 등록·수정만 로그인)

#### US-001: 회원가입 [Must]
As a 방문자, I want 이메일/비밀번호로 회원가입, so that 내 레시피와 재료를 개인 계정에 저장할 수 있다.
**수용 기준**
- Given 미가입 방문자 When 유효한 이메일·비밀번호로 가입 요청 Then 계정이 생성되고 로그인 상태가 된다
- Given 이미 등록된 이메일 When 동일 이메일로 가입 시도 Then 중복 안내 메시지가 표시되고 가입이 거부된다

#### US-002: 로그인 / 로그아웃 [Must]
As a 회원, I want 로그인·로그아웃, so that 내 데이터에 안전하게 접근하고 세션을 종료할 수 있다.
**수용 기준**
- Given 가입된 회원 When 올바른 자격증명으로 로그인 Then 인증되어 등록·수정 기능이 활성화된다
- Given 잘못된 자격증명 When 로그인 시도 Then 실패 안내가 표시되고 인증되지 않는다
- Given 로그인 상태 When 로그아웃 Then 세션이 종료되고 열람 전용 상태로 돌아간다

#### US-003: 비로그인 열람 및 로그인 게이트 [Must]
As a 방문자, I want 로그인 없이 레시피를 열람, so that 가입 전에 서비스를 둘러볼 수 있다. 단 등록·수정은 로그인 후에만 가능하다. *(Q4-c)*
**수용 기준**
- Given 비로그인 방문자 When 레시피 목록/상세를 조회 Then 로그인 없이 열람할 수 있다
- Given 비로그인 방문자 When 등록/수정/삭제를 시도 Then 로그인 화면으로 유도되고 동작은 수행되지 않는다

### 레시피 관리 (Q2-a)

#### US-004: 레시피 등록 [Must]
As a 회원, I want 제목·조리 단계·사진(선택)·카테고리와 재료를 포함한 레시피를 등록, so that 내 레시피를 구조화해 보관한다. *(Q2-a, 사진은 Q6-a에 따라 선택 항목)*
**수용 기준**
- Given 로그인 회원 When 제목·조리 단계를 입력하고 저장 Then 레시피가 내 계정에 생성되어 목록에 나타난다
- Given 필수값(제목) 누락 When 저장 시도 Then 검증 오류가 표시되고 저장되지 않는다
- Given 사진 미첨부 When 저장 Then 사진 없이도 정상 저장된다 (사진은 선택)

#### US-005: 레시피 목록·상세 조회 [Must]
As a 사용자, I want 레시피 목록과 상세를 조회, so that 등록한 레시피 내용을 확인한다.
**수용 기준**
- Given 레시피가 존재 When 목록 화면 진입 Then 레시피들이 제목·대표정보와 함께 표시된다
- Given 특정 레시피 When 상세 진입 Then 제목·재료·조리 단계·사진(있으면)·카테고리가 모두 표시된다

#### US-006: 레시피 수정 [Must]
As a 회원, I want 내 레시피를 수정, so that 내용을 최신 상태로 유지한다.
**수용 기준**
- Given 내가 등록한 레시피 When 필드를 수정하고 저장 Then 변경 내용이 상세에 반영된다
- Given 다른 회원의 레시피 When 수정 시도 Then 권한 없음으로 차단된다

#### US-007: 레시피 삭제 [Must]
As a 회원, I want 내 레시피를 삭제, so that 불필요한 레시피를 정리한다.
**수용 기준**
- Given 내가 등록한 레시피 When 삭제 확인 Then 레시피가 목록에서 제거된다
- Given 다른 회원의 레시피 When 삭제 시도 Then 권한 없음으로 차단된다

### 식재료 관리 (Q2-b, Q5)

#### US-008: 식재료 마스터 등록·관리 [Must]
As a 회원, I want 식재료(이름·분류·기본 단위)를 마스터 목록으로 등록·수정·삭제, so that 레시피와 재고에서 재사용해 오타·중복을 막는다. *(Q2-b, Q5-c의 "마스터에서 선택" 전제)*
**수용 기준**
- Given 로그인 회원 When 재료명·분류·단위를 입력해 저장 Then 식재료가 마스터 목록에 추가된다
- Given 동일 이름의 재료가 이미 존재 When 중복 등록 시도 Then 중복 안내가 표시된다
- Given 레시피/재고에서 참조 중인 재료 When 삭제 시도 Then 참조 영향이 안내된다

#### US-009: 레시피에 식재료 연결 [Must]
As a 회원, I want 레시피 작성 시 식재료 마스터에서 재료를 선택해 수량과 함께 연결, so that 재료 데이터가 구조화되어 검색·재고 대조에 쓰인다. *(Q5-c)*
**수용 기준**
- Given 레시피 편집 화면 When 마스터에서 재료를 검색·선택하고 수량을 입력 Then 해당 재료가 레시피 재료 목록에 연결된다
- Given 마스터에 없는 재료 When 새 재료명을 입력 Then 마스터에 신규 등록 후 연결하도록 안내된다

### 검색 (Q2-d)

#### US-010: 레시피 검색·필터 [Must]
As a 사용자, I want 레시피를 이름·카테고리·재료 기준으로 검색·필터, so that 원하는 레시피를 빠르게 찾는다. *(Q2-d)*
**수용 기준**
- Given 레시피가 존재 When 이름 키워드로 검색 Then 일치하는 레시피만 목록에 표시된다
- Given 카테고리/재료 필터 선택 When 적용 Then 조건에 맞는 레시피만 표시된다
- Given 일치 결과 없음 When 검색 Then 빈 결과 안내가 표시된다

### 재고 관리 & 부족 재료 대조 (Q2-c, Q5-c)

#### US-011: 보유 식재료(재고) 관리 [Should]
As a 회원, I want 내가 보유한 식재료의 수량·유통기한을 등록·수정, so that 집에 있는 재료를 파악한다. *(Q2-c)*
**수용 기준**
- Given 로그인 회원 When 마스터 재료를 선택해 보유 수량·유통기한을 저장 Then 내 재고 목록에 추가된다
- Given 재고 항목 When 수량을 0으로 수정 또는 삭제 Then 보유 목록에서 제거/소진 처리된다

#### US-012: 레시피 상세에서 부족한 재료 표시 [Should]
As a 회원, I want 레시피 상세에서 내 재고와 대조해 부족한 재료를 표시, so that 무엇을 더 사야 하는지 알 수 있다. *(Q5-c)*
**수용 기준**
- Given 재고 데이터가 있는 로그인 회원 When 레시피 상세 진입 Then 레시피 재료 중 재고가 없거나 수량이 부족한 항목이 "부족"으로 표시된다
- Given 모든 재료를 충분히 보유 When 상세 진입 Then "재료 충족"으로 표시된다
- Given 비로그인 방문자 When 상세 진입 Then 부족 재료 표시는 숨겨지고 로그인 시 제공됨을 안내한다

### 추천 (Q2-e)

#### US-013: 보유 재료 기반 레시피 추천/필터 [Could]
As a 회원, I want 내 보유 재료로 만들 수 있는(또는 거의 만들 수 있는) 레시피를 추천·필터, so that 지금 있는 재료를 활용한다. *(Q2-e)*
**수용 기준**
- Given 재고 데이터가 있는 로그인 회원 When "만들 수 있는 레시피" 필터 적용 Then 보유 재료로 모든 재료가 충족되는 레시피만 표시된다
- Given 일부만 보유 When 추천 목록 조회 Then 부족 재료 수가 적은 순으로 정렬되어 표시된다

## 5. 확인 필요 (Open Questions)
- **[범위/일정] — 확정됨 (2026-07-24 사용자 승인)**: 계층화 동의. Must(US-001~010) 1차 출시 → Should(US-011~012) → Could(US-013) 순차 진행.
- **[데이터] — 확정됨 (2026-07-24 사용자 승인)**: 식재료 마스터는 **회원 개인별** 마스터로 구성한다 (전 회원 공용 아님).
- **[데이터] (미해결, 이후 과제)**: 재고 수량 단위와 레시피 요구 수량 단위의 환산(예: g ↔ 개) 정책 미정. US-012 "부족" 판정은 동일 단위 기준으로 우선 구현하고, 단위 환산은 이후 과제로 이관.
- **[비기능] (designer/backend 단계 확정)**: 사진 저장 방식·용량 상한 미정. 소규모(Q6-a) 기준 사진은 선택 항목이며 상세 정책은 G2에서 확정.

## 6. 비기능 요구사항 (참고)
- **플랫폼**: PC·모바일 반응형 모두 대응 *(Q7-c)* — 모든 주요 화면은 모바일 뷰포트에서도 사용 가능해야 한다.
- **규모**: 소규모(레시피 수백 개 이하), 사진 선택적 *(Q6-a)*.
- **외부 제약**: 특별한 외부 시스템 연동·법적 제약 없음 *(Q7-c)*.

## v2.3.0-1. 배경 & 목표
- **요청**: `design/v2.0.0/레시피 상자.html` 목업 기능 중 현재 7개 화면에 없는 것을 v2.3.0으로 추가한다.
- **목표**: (①) 흩어진 레시피/재고 데이터를 한눈에 보는 홈 대시보드를 제공하고, (②) "부족 재료→재고 추가→만들 수 있는 레시피"로 이어지는 실사용 동선을 연결하며, (③) 레시피·식재료·재고에 실사용에 필요한 도메인 필드(조리시간·별점·별칭·칼로리·보관방법·보관위치)를 추가한다.

  - 홈 대시보드 KPI/패널 수치가 원본 데이터(레시피/마스터/재고)와 **100% 일치**(집계 정확도).
  - 상세 "부족 재료→재고 추가→만들 수 있는 레시피 재진입" 플로우가 이탈 없이 연결됨.
  - 신규 필드(조리시간·별점·보관정보) 입력·정렬이 **기존 화면 회귀 없이** 동작(`./harness/check.sh` 통과).

```
        │
        ├─→ ① 홈 대시보드 (US-018)          : KPI/패널이 조리시간·매칭 집계를 표기
        └─→ ② UX 연결 (US-019~022)          : 매칭률·역탐색·위저드가 재고/재료 필드에 의존
```
- 구현 순서 권고: US-014~017(③) → US-018(①) → US-019~022(②).
- 매칭 판정("지금 만들 수 있는")은 **매칭률 100%만** *(Q3 (a))* — 모든 필요 재료를 동일 단위 비교(v1 US-012 규칙 승계)로 충족. **유통기한·보관위치는 매칭 판정에 반영하지 않는다**(유통기한 임박은 별도 KPI/패널 D-3로 분리 노출).

## v2.3.0-3. Non-goals (이번에 하지 않는 것)
- 조직/워크스페이스 스위처 *(Q5 → 제외)*
- 다국어(i18n) 전환 *(Q5 → 제외)*
- 카드형/리스트형·내비 레이아웃 토글 등 목업 데모용 prop *(Q5 → 제외, 디자인툴 전용 장치)*
- **별점 리뷰 텍스트/코멘트** — 이번엔 **평점 수치(1~5)만**, 코멘트·리뷰 본문은 제외 *(Q5 답변 단서)*
- 단위 환산(g↔개) — v1 Open Question 그대로 유예(매칭·부족 판정은 동일 단위 비교)
> ⚠️ **범위 확대 주의(v1 Non-goal 일부 해제)**: v1에서 "소셜 기능"과 "칼로리 계산"은 Non-goal이었으나, 사용자가 v2.3.0에서 **회원별 별점 집계**(Q2 (b))와 **마스터 100g당 칼로리 필드**(③)를 명시 선택했다. 따라서 이 두 항목에 한해 v1 Non-goal을 **해제**한다. 단 칼로리는 "마스터 참고 필드"이며 레시피 영양 자동 계산은 아니다.

## v2.3.0-4. 유저스토리 (US-014 ~ US-022)

### ③ 신규 도메인 필드 (선행) — 모두 [Must]

#### US-014: 레시피 조리시간(cook time) *(Q1 (a))* [Must]
As a 회원, I want 레시피에 조리시간(분)을 입력하고 목록/상세에서 보고 정렬, so that 시간 기준으로 레시피를 고를 수 있다.
**AC**
- Given 로그인 회원 When 레시피 등록/수정 폼에 조리시간(분, 정수)을 입력·저장 Then 값이 저장되고 상세·목록에 "N분"으로 표시된다 *(recipe-detail 목업 dmeta "15분")*
- Given 조리시간 미입력 When 저장 Then 값 없이 정상 저장되고 표시에서 생략된다 (nullable, Q4-a)
- Given 목록에서 정렬="조리시간 짧은순" When 적용 Then 조리시간 오름차순 정렬되며, 값이 없는 레시피는 뒤로 배치된다
- Given 비로그인 방문자 When 목록/상세 열람 Then 조리시간 "N분" **표기는 공개**된다(레시피 귀속 공개 정보). 단 조리시간 **입력**(등록/수정 폼)은 로그인 필수 *(2026-07-26 사용자 결정: 조리시간 공개 표시, Open Question #1 해소)*

#### US-015: 레시피 별점 — 회원별 평점 집계 *(Q2 (b))* [Must]
As a 회원, I want 레시피에 별점(1~5)을 남기고 평균 평점과 평가 수를 보고 정렬, so that 여러 회원의 평가로 레시피 품질을 가늠한다.
**AC**
- Given 로그인 회원 When 레시피 상세에서 별점(1~5)을 선택·저장 Then 그 회원의 평점이 저장되고 레시피 **평균 평점·평가 수**가 갱신된다
- Given 이미 평점을 남긴 회원 When 같은 레시피에 다시 평점 저장 Then 값이 **갱신**되고 평가 수는 증가하지 않는다 (**1인 1평점**, 재평가 시 갱신)
- Given 아직 평가가 0건인 레시피 When 상세/목록 표시 Then "평가 없음"으로 표시되고 평균은 계산에서 제외된다
- Given 목록에서 정렬="평점 높은순" When 적용 Then 평균 평점 내림차순 정렬되며, 평가 없는 레시피는 뒤로 배치된다
- Given 비로그인 방문자 When 목록/상세 열람 Then **평균 평점·평가 수 표기는 공개**된다(레시피 귀속 공개 정보). 단 별점 **입력**은 로그인 필수 — 비로그인이 입력 시도 시 로그인 유도 *(2026-07-26 사용자 결정: 평균 평점 공개 표시, Open Question #1 해소)*

#### US-016: 식재료 마스터 확장 필드 *(③)* [Must]
As a 회원, I want 마스터 식재료에 별칭·100g당 칼로리·기본 보관방법·메모를 함께 관리, so that 재료 검색·표준화·보관 안내가 풍부해진다. *(ingredient-master 목업: "이름·별칭·분류·기본 단위·kcal")*
**AC**
- Given 로그인 회원 When 마스터 등록/수정에서 별칭(복수 가능)·100g당 칼로리(kcal)·기본 보관방법(냉장/냉동/실온)·메모를 입력·저장 Then 값이 저장되고 마스터 상세에 표시된다
- Given 별칭이 입력된 재료 When 마스터/레시피 재료 검색에서 별칭으로 검색 Then 해당 재료가 검색된다
- Given 신규 필드 미입력 When 저장 Then 전부 빈 값으로 정상 저장된다 (모두 nullable, Q4-a; 기존 마스터 데이터는 NULL 유지, 백필 없음)
- Given 기본 보관방법 값 When 저장 Then 냉장/냉동/실온 3종 중 하나로만 저장된다(그 외 거부)

#### US-017: 재고 보관위치 *(③)* [Must]
As a 회원, I want 내 재고 항목에 보관위치(냉장실/냉동실/실온)를 지정, so that 어디에 뒀는지 관리하고 재고 화면에서 구분한다.
**AC**
- Given 로그인 회원 When 재고 등록/수정에서 보관위치(냉장실/냉동실/실온)를 선택·저장 Then 값이 저장되고 재고 목록에 표시된다
- Given 보관위치 미선택 When 저장 Then 값 없이 정상 저장된다 (nullable, Q4-a; 기존 재고 데이터 NULL 유지)
- Given 보관위치 값 When 저장 Then 냉장실/냉동실/실온 3종 중 하나로만 저장된다
- **주의**: 보관위치는 **매칭 판정에 반영하지 않는다** *(Q3 (a))* — 표시·관리 용도.

### ① 홈/대시보드 — [Must]

#### US-018: 홈 대시보드 (개요) *(①)* [Must]
As a 로그인 회원, I want 홈에서 KPI 4종과 패널 3종으로 내 레시피/재고 현황을 한눈에 보기, so that 오늘 뭘 만들 수 있고 뭘 챙겨야 하는지 즉시 파악한다.
**AC** (home 목업 근거)
- Given 로그인 회원 When 홈 진입 Then `개요` 내비 그룹의 홈 라우트가 열리고 아래 KPI 4종이 표시된다:
  - **등록 레시피** 수 (예: "12개", 카테고리 분포 부가) *(home line 254)*
  - **지금 만들 수 있는 레시피** = 매칭률 100% 레시피 수(성공색) *(line 259·262 "매칭률 100%만 집계")*
  - **내 재고** 종수 *(line 265)*
  - **임박 재료(D-3)** 종수(경고색, design-guide §6 D-day 규칙) *(line 270)*
- Given 홈 진입 When 패널 렌더 Then 패널 3종이 표시된다: **지금 만들 수 있는 레시피**(매칭률 100%, 조리시간·보유 N/N 표기), **유통기한 임박**(D-day 배지), **최근 추가한 레시피** *(line 279·311·324)*
- Given 각 KPI/패널 값 When 원본 데이터(레시피/마스터/재고)와 대조 Then **100% 일치**한다 (집계 정확도, Q7-a)
- Given 비로그인 방문자 When 홈 접근 Then 로그인 필수로 게이트된다 (개인 재고 기반, Q6-b)

### ② UX 연결 강화

#### US-019: 상세 "요리 시작" + 부족 재료→재고 추가 연결 *(②)* [Should]
As a 로그인 회원, I want 레시피 상세에서 부족한 재료를 바로 재고에 추가(및 요리 시작 진입), so that 부족분을 채워 조리로 이어간다. (현재 "확장 예정" 자리 대체)
**AC**
- Given 재고 대조 결과 부족 재료가 있는 로그인 회원 When 상세에서 "부족한 재료 추가하기" 실행 Then 해당 부족 재료가 채워진 상태로 재고 추가 흐름(US-022 위저드)으로 연결된다
- Given 상세 When "요리 시작" 실행 Then 조리 진행 화면/모드로 진입한다 *(recipe-detail line 280 버튼)*
- Given 모든 재료 충족(부족 0) When 상세 진입 Then "부족한 재료 추가하기"는 숨김/비활성되고 요리 시작만 노출된다
- Given 비로그인 방문자 When 상세 진입 Then 재고 기반 연결 기능은 숨김(로그인 유도), 기존 상세 열람은 유지 (US-003·Q6-b)

#### US-020: 상세 매칭률 진행 바(progress bar) *(②)* [Should]
As a 로그인 회원, I want 상세에서 보유/필요 재료 매칭률을 진행 바로 보기, so that 얼마나 준비됐는지 시각적으로 안다.
**AC**
- Given 재고 있는 로그인 회원 When 상세 진입 Then "보유 X / 필요 Y" 수치와 매칭률 진행 바가 표시된다 *(recipe-detail line 127 진행 바)*
- Given 매칭률 100% When 표시 Then 성공색 + "지금 가능" 배지가 노출된다 *(home matchrow 규칙과 동일)*
- Given 비로그인/재고 0건 When 상세 진입 Then 진행 바는 숨김 (v1 US-012 게이트 승계)

#### US-021: 재고행 → "이 재료로 만들 수 있는 레시피" 역탐색 *(②)* [Should]
As a 로그인 회원, I want 재고 화면에서 특정 재료로 만들 수 있는 레시피를 역으로 찾기, so that 가진 재료를 소비할 레시피를 빠르게 찾는다.
**AC**
- Given 재고 목록의 한 재료행 When "이 재료로 만들 수 있는 레시피" 실행 Then 그 재료를 사용하는 레시피 목록으로 이동한다 (기존 `GET /recipes?ingredient_id=` 계약 활용)
- Given 결과 없음 When 역탐색 Then 빈 결과 안내가 표시된다
- Given 비로그인 방문자 When 재고 화면 접근 Then 로그인 필수 (개인 재고, Q6-b)

#### US-022: 재고 추가 다단계 위저드 + 완료 후 추천 *(②)* [Could]
As a 로그인 회원, I want 재고를 단계별 위저드로 추가하고 완료 후 새로 만들 수 있게 된 레시피를 안내받기, so that 추가한 재료의 효용을 바로 확인한다.
**AC**
- Given 로그인 회원 When 재고 추가 위저드 진입 Then 재료 선택→수량/단위→유통기한/보관위치 등 단계로 나뉘어 입력한다
- Given 위저드 완료 When 저장 Then 재고가 추가되고 "이제 이런 레시피를 만들 수 있어요"로 **새로 매칭률 100%가 된 레시피**를 안내한다
- Given 새로 가능해진 레시피가 없음 When 완료 Then 추가 완료만 안내하고 추천 섹션은 생략한다
- Given US-019에서 부족 재료를 들고 진입 When 위저드 시작 Then 해당 재료가 미리 채워진 상태로 시작한다 (US-019 연계)

## v2.3.0-5. 데이터 & 계약 영향 요약 (backend-dev G2 입력용)
> planner는 구현을 결정하지 않는다. 아래는 **영향 범위 개괄**이며 스키마/엔드포인트 확정은 backend-dev(G2·G3) 몫이다. 모든 신규 컬럼은 **nullable, 백필 없음** *(Q4-a)*, 신규 엔드포인트는 **additive** (기존 계약 불변).

**신규/변경 테이블·컬럼 (후보)**
- `recipes` + `cook_time_minutes INTEGER NULL` (US-014)
- **신규 테이블 `recipe_ratings`** (US-015, 회원별 집계이므로 recipes 컬럼이 아닌 **별도 테이블**): `id`(예 `rrt_`)·`recipe_id` FK·`user_id` FK·`score INTEGER(1..5)`·타임스탬프·`deleted_at`. **UNIQUE(recipe_id, user_id) WHERE deleted_at IS NULL** (1인 1평점, 재평가 갱신). 평균·평가수는 집계(조회 시 계산 또는 캐시).
- `ingredients` + `aliases`(별칭, 복수)·`kcal_per_100g REAL NULL`·`default_storage`(냉장/냉동/실온)·`memo TEXT NULL` (US-016)
- `inventory_items` + `storage_location`(냉장실/냉동실/실온, NULL) (US-017)

**openapi(api/openapi.yaml) 영향 (후보)**
- `RecipeDetail`/`RecipeListItem` + `cook_time_minutes`, + `rating {average, count}` (읽기)
- `RecipeWriteRequest` + `cook_time_minutes`
- 별점 입력용 신규 엔드포인트(예: `PUT /recipes/{id}/rating`) — 로그인 필수, 1인 1평점 upsert
- `RecipeListParams.sort` + `rating_desc`·`cook_time_asc` (정렬 옵션 additive)
- `Ingredient`/`IngredientWriteRequest` + 별칭·kcal·기본보관방법·메모
- `InventoryItem` + `storage_location`
- 홈 대시보드 집계용 신규 엔드포인트(예: `GET /dashboard` 또는 `GET /home/summary`) — KPI 4종·패널 3종 집계 반환, 로그인 필수
- 역탐색(US-021)은 기존 `GET /recipes?ingredient_id=` 활용(신규 계약 불필요), 매칭 집계는 `available_only`/`makeable` 계열 활용
> **types.ts 주의**: 현재 `web/src/api/types.ts` 주석은 "계약에 없는 필드 추가 금지(예: cookTime)"라고 명시한다. v2.3.0에서 조리시간·별점이 계약에 정식 추가되면 이 금지 주석과 타입을 **계약 반영 후** 갱신해야 한다(frontend-dev G4).

## v2.3.0-6. MoSCoW 계층화 & 회귀 영향
| 계층 | 스토리 |
|---|---|
| **Must** | US-014 조리시간 · US-015 별점(회원 집계) · US-016 마스터 확장 · US-017 재고 보관위치 · US-018 홈 대시보드 |
| **Should** | US-019 부족재료→재고추가 연결 · US-020 매칭률 진행바 · US-021 재고 역탐색 |
| **Could** | US-022 재고 추가 위저드 + 완료 후 추천 |
| **Won't(이번 제외)** | 조직 스위처 · 다국어 · 레이아웃 토글 prop · 별점 리뷰 코멘트 텍스트 · 단위 환산 |

**회귀 영향 (regression-harness 준수)**
- 기존 7개 화면·기능은 **불변 자산**. 신규 기능은 Additive-Only(기존 파일 수정 금지, 신규 라우트/컴포넌트/컬럼/엔드포인트로만 추가).
- 신규 DB 컬럼은 전부 **nullable + 백필 없음** → 기존 데이터·조회 경로 무영향.
- 신규 엔드포인트/정렬 옵션은 additive → 기존 계약 소비자 무영향.
- 모든 구현 에이전트는 완료 전 `./harness/check.sh` 통과 필수(Q7-c).
