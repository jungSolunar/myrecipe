# 요구사항 인터뷰: 레시피 & 식재료 관리 웹서비스
상태: CLOSED
라운드: 1/2 (1라운드로 충분 — 핵심 불확실성 없음, Phase 2 진행)

## 요청 원문
"레시피 등록 및 관리, 식재료 관리를 하는 웹서비스를 구성하려고 해."

## 내가 이해한 것 (확인용 요약)
- 웹 기반 서비스로, 레시피를 **등록·조회·수정·삭제**하고 관리할 수 있다.
- 식재료(재료)를 **관리**하는 기능이 함께 있다 (재료 목록/재고/보유 여부 등으로 추정).
- 레시피와 식재료가 서로 **연동**될 가능성이 있다 (예: 레시피가 어떤 재료를 쓰는지).
- 아직 대상 사용자, 인증 필요 여부, 기능의 정확한 범위, 데이터 규모는 정해지지 않았다.
> 위 이해가 틀렸다면 답변 섹션에 바로잡아 주세요.

## 질문

### Q1. [사용자] 이 서비스의 주 사용자는 누구인가요?
- (a) 개인 사용자 1명 (나만의 레시피/식재료를 기록·관리하는 개인용)
- (b) 여러 일반 회원 (각자 자기 레시피/재료를 관리하는 다수 가입자)
- (c) 팀/가족 등 공유 그룹 (여러 명이 같은 레시피·재료를 함께 관리)
- (d) 관리자가 콘텐츠를 등록하고 일반 방문자는 열람만 (예: 레시피 공개 사이트)
- (e) 기타: ___
- 기본 가정: (b) 여러 일반 회원 — 답이 없으면 이 가정으로 진행합니다

### Q2. [범위] 이번 버전(MVP)에 반드시 포함해야 하는 핵심 기능은 무엇인가요? (해당하는 것 모두)
- (a) 레시피 CRUD (제목·재료·조리 단계·사진 등록/수정/삭제)
- (b) 식재료 CRUD (재료명·분류·단위 등 기본 관리)
- (c) 식재료 재고/보유 관리 (수량, 유통기한 등)
- (d) 레시피 검색·필터 (재료·카테고리·이름 기준)
- (e) 보유 재료로 만들 수 있는 레시피 추천/필터
- (f) 기타: ___
- 기본 가정: (a)+(b)+(d) 를 MVP 필수로, (c)·(e)는 이후 단계(Should/Could)로 진행합니다

### Q3. [범위] 이번 버전에서 **제외**할(하지 않을) 기능이 있나요? (Non-goals 후보)
- (a) 장보기 목록/자동 쇼핑리스트 생성
- (b) 영양성분·칼로리 계산
- (c) 다른 사용자와의 레시피 공유/공개·댓글·좋아요 등 소셜 기능
- (d) 식단 캘린더/주간 식단 플래너
- (e) 외부 쇼핑몰·배달 연동
- (f) 특별히 없음 / 위 항목 중 일부는 포함하고 싶음: ___
- 기본 가정: (a)(b)(c)(d)(e) 전부 이번 범위에서 제외 — 답이 없으면 MVP는 레시피·식재료 관리 핵심만 다룹니다

### Q4. [사용자] 로그인·회원가입(인증)이 필요한가요?
- (a) 필요 (개인별 데이터 분리, 로그인 후 이용)
- (b) 불필요 (로그인 없이 누구나 사용, 데이터는 공용/브라우저 저장)
- (c) 열람은 자유, 등록·수정만 로그인 필요
- (d) 기타: ___
- 기본 가정: (a) 필요 — Q1이 다수 회원이면 개인별 데이터 분리를 위해 인증이 필요합니다

### Q5. [데이터] 레시피와 식재료를 어떻게 연동하고 싶으신가요?
- (a) 레시피에 재료를 자유 텍스트로만 입력 (연동 없음, 단순 목록)
- (b) 식재료 마스터 목록에서 선택해 레시피에 연결 (재료 재사용, 오타 방지)
- (c) (b)에 더해 보유 재고와 대조해 "부족한 재료" 표시까지
- (d) 기타: ___
- 기본 가정: (b) 식재료 마스터에서 선택해 연결 — 재료 데이터를 구조화해 검색·재사용이 가능하게 합니다

### Q6. [데이터] 예상 데이터 규모와 첨부(사진 등)는 어느 정도인가요?
- (a) 소규모 (레시피 수백 개 이하, 사진 선택적, 개인/소수용)
- (b) 중간 규모 (수천~수만 개, 사진 필수, 다수 회원)
- (c) 대규모 서비스 지향 (수십만 개 이상, 미디어 다수)
- (d) 아직 모름
- 기본 가정: (a) 소규모 — 답이 없으면 소규모 기준으로 범위·성능 목표를 잡습니다

### Q7. [제약] 이용 환경(플랫폼)과 특별한 제약이 있나요?
- (a) PC 웹 중심
- (b) 모바일 웹 중심 (주방/장보기 상황에서 휴대폰 사용)
- (c) PC·모바일 반응형 모두 대응
- (d) 일정/기존 시스템 연동/정책 등 제약: ___
- 기본 가정: (c) 반응형 모두 대응, 특별한 외부 연동·법적 제약 없음 — 다르면 알려주세요

# 요구사항 인터뷰: v2.3.0 레시피 상자 기능 확장
상태: CLOSED
라운드: 1/2 (1라운드로 충분 — 7개 답변으로 핵심 불확실성 해소, Phase 2 PRD 반영 완료 → docs/prd.md v2.3.0 섹션)

## 요청 원문
"design/v2.0.0/레시피 상자.html 목업에 있는 기능 중 현재 화면에 없는 것을 v2.3.0으로 추가 구현한다."

## 내가 이해한 것 (확인용 요약)
- 현재 7개 화면(로그인·회원가입·레시피목록·레시피상세·레시피폼·식재료마스터·내재고)에 **없는** 목업 기능을 v2.3.0으로 추가한다.
- 오케스트레이터와 사용자가 확정한 범위는 **① + ② + ③ 전체**다.
  - **① 홈/대시보드 신규 화면**: `개요` 내비 그룹 + 홈 라우트 신설, KPI 4종(등록 레시피 수 / 지금 만들 수 있는 레시피(매칭률 100%) / 내 재고 종수 / 임박 재료 D-3), 패널 3종(만들 수 있는 레시피 · 유통기한 임박 · 최근 추가). 기존 데이터 집계, 신규 도메인 0.
  - **② UX 연결 강화**(기존 openapi 계약 내, DB/BE 변경 없음): 상세의 `요리 시작` + `부족한 재료 추가하기`(부족→재고추가 연결), 매칭률 progress bar, 재고행→`이 재료로 만들 수 있는 레시피` 역탐색, 재고 추가 다단계 위저드 + 완료 후 "이제 이런 레시피를 만들 수 있어요".
  - **③ 신규 도메인 필드**(DB+openapi+BE+FE 전면 변경): 레시피 별점(rating)+정렬, 레시피 조리시간(cook time)+정렬, 식재료 마스터 별칭(alias)·100g당 칼로리·기본 보관방법(냉장/냉동/실온)·메모, 재고 보관위치(냉장실/냉동실/실온).
- 기존 화면·기능은 불변 자산이며 추가는 Additive-Only(기존 파일 수정 금지) 원칙을 따른다.
- 아래 질문은 **범위 자체(①②③ 채택 여부)를 다시 묻는 것이 아니라**, 구현에 앞서 반드시 정해야 하는 세부 규칙·충돌·경계만 확인한다.
> 위 이해가 틀렸다면 답변 섹션에 바로잡아 주세요.

## 질문

### Q1. [제약] 목업 스펙 충돌 — 홈 대시보드의 조리시간(`15분`) 표기 처리
home.html은 "새 도메인 가정 없이 집계"(line 377)라고 하면서도 '지금 만들 수 있는 레시피' 카드에 `15분/10분/12분` 조리시간을 노출합니다(line 285·293·301). 조리시간은 ③(신규 도메인 필드)에 속하므로 충돌합니다. 어떻게 정리할까요?
- (a) ③의 레시피 조리시간(cook time)을 **먼저 도입한 뒤** 대시보드가 그 값을 표기 (③가 ①의 선행 의존)
- (b) 대시보드 1차에서는 **조리시간 표기를 빼고**(도메인 0 유지), 조리시간 컬럼이 생긴 뒤 후속으로 노출
- (c) 기타: ___
- 기본 가정: (a) — ①②③를 한 릴리스로 함께 내므로 조리시간 컬럼이 어차피 생기며, 대시보드가 그 값을 그대로 표기하는 편이 목업과 일치합니다. (일정상 대시보드를 먼저 떼어내고 싶다면 (b)를 선택하세요.)

### Q2. [데이터] 레시피 별점(rating)의 입력 주체
③의 레시피 별점을 누가 매기나요? 이 선택이 도메인 규모를 크게 좌우합니다.
- (a) **소유자 자기평가 단일값** — 레시피 소유자가 자기 레시피에 별 1개 값을 저장(recipes 컬럼 1개, 회원별 평가 테이블 불필요)
- (b) **회원별 평점 집계** — 여러 회원이 각자 별점을 남기고 평균/개수를 집계(별도 ratings 테이블·중복방지·집계 로직 필요, 도메인 대폭 확대)
- (c) 별점은 회원 입력이 아니라 **표시만**(예: 목업 상 정적 표시), 입력 기능 없음
- (d) 기타: ___
- 기본 가정: (a) 소유자 자기평가 단일값 — 현재 서비스는 "각자 자기 레시피를 관리"(v1 Q1-b)하고 소셜 기능은 Non-goal이므로, 회원별 평점 집계(b)는 소셜 성격이 강해 이번 범위에서 제외하는 것이 정합적입니다.

### Q3. [데이터] "지금 만들 수 있는 레시피"의 판정 정의
대시보드 KPI·패널과 상세 매칭률, 재고 역탐색이 공유하는 "만들 수 있다"의 기준을 확정해야 합니다.
- (a) **매칭률 100%만**(모든 재료 보유, 현행 US-012/013 부족판정 = 동일 단위 비교 규칙 그대로). 유통기한·보관위치는 판정에 **반영 안 함**
- (b) (a) + **유통기한 만료분 제외**(expires_at 지난 재고는 "없음"으로 간주해 매칭에서 빠짐)
- (c) (a) + 유통기한 + **보관위치 규칙까지** 반영(예: 특정 보관위치 재료만 인정 등)
- (d) 기타: ___
- 기본 가정: (a) 매칭률 100%만 — home.html이 "매칭률 100%만 집계"(line 262)로 명시하고, 유통기한 임박은 별도 KPI/패널(D-3)로 이미 분리 노출되므로 매칭 판정과 유통기한 판정을 섞지 않는 편이 단순하고 목업과 일치합니다. (신선도까지 반영하려면 (b).)

### Q4. [데이터] 마스터·재고 신규 필드의 필수/선택 여부와 기존 데이터 마이그레이션
③의 신규 필드(마스터: 별칭·100g당 칼로리·기본 보관방법·메모 / 재고: 보관위치)를 기존에 이미 등록된 레시피·마스터·재고 데이터에 어떻게 적용할까요?
- (a) **전부 선택(nullable)** — 기존 데이터는 빈 값으로 두고, 새로 입력할 때만 채움(마이그레이션은 컬럼 추가만, 백필 없음)
- (b) **일부 필수** — 예: 재고 보관위치나 기본 보관방법은 필수로 하고 기존 데이터에 기본값(예: '냉장')을 일괄 백필
- (c) 기타(필드별로 다르게): ___
- 기본 가정: (a) 전부 선택(nullable), 기존 데이터 백필 없음 — Additive-Only·회귀 방지 원칙상 기존 데이터/입력 흐름을 강제 변경하지 않는 것이 안전합니다. (특정 필드를 필수로 원하면 어떤 필드인지와 기본 백필값을 알려주세요.)

### Q5. [범위] 이번에 명시적으로 **제외**할 것(Non-goals) 확인
목업 번들에는 디자인툴 전용 장치도 섞여 있습니다. 아래를 이번 v2.3.0 Non-goals로 확정할까요? (제외에 동의하지 않는 항목만 표시)
- (a) 조직/워크스페이스 스위처
- (b) 다국어(i18n) 전환
- (c) 카드형/리스트형·내비 레이아웃 토글 등 목업 데모용 prop
- (d) 별점의 회원별 공개 집계·리뷰/댓글(= Q2에서 (a)/(c) 선택 시 자동 제외)
- (e) 위 전부 제외에 동의 / 일부는 포함하고 싶음: ___
- 기본 가정: (a)(b)(c)(d) 전부 이번 범위에서 제외 — 이들은 기존 PRD Non-goals(소셜·다국어 미언급) 및 소규모(v1 Q6-a) 기조와 일치합니다.

### Q6. [사용자] 신규 기능의 비로그인 열람 권한(기존 US-003 게이트 정합)
현행 정책은 "열람 자유, 등록·수정만 로그인"(v1 Q4-c, US-003)이고, 부족재료 대조(US-012)는 로그인+재고 있을 때만 제공됩니다. 신규 기능들의 비로그인 노출은 어떻게 할까요?
- (a) **개인화 기능은 로그인 필수, 공개 정보만 비로그인 열람** — 홈 대시보드·재고 역탐색·매칭률·부족재료추가는 개인 재고 기반이라 로그인 필요 / 별점·조리시간 등 레시피 자체 정보는 비로그인 열람 시에도 표시
- (b) 신규 기능 **전부 로그인 필수**(홈이 로그인 후 첫 화면 성격)
- (c) 기타: ___
- 기본 가정: (a) — 개인 재고에 의존하는 기능(대시보드 KPI·역탐색·매칭률·부족재료)은 US-012 선례대로 로그인 게이트, 별점·조리시간처럼 레시피에 귀속된 공개 정보는 US-003 열람 자유를 유지하는 것이 기존 게이트와 정합적입니다.
